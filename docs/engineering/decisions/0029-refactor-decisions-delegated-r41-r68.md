# Decision 0029: Choices made while delivering refactor items R-41 to R-68

**Date:** 2026-11-15. **Authority:** the owner, by delegation. They asked to work "from R-41 to R-68" of [the code-quality review's refactor plan](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md) and to "take responsible and senior and hard decisions that require a human interaction for me". Decisions [0027](0027-refactor-decisions-delegated.md) and [0028](0028-refactor-decisions-delegated-r21-r40.md) record the same delegation for R-01 to R-40, and their principles carry over: where two options are close, choose the one that is reversible, fails closed on money and permissions, and changes no stored hash or accepted scenario.

| # | Item | Choice | Why |
|---|---|---|---|
| **F1. Who owns the workflow label rule** | [R-43](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-43) | The domain's `ir_normalized` owns WF-06's label rule. The editor keeps one copy, in `apps/web/lib/workflow-ir.ts`, tested against shared fixtures that the Python tests also read, so the two can't disagree on any case. A label-free normalized graph is not adopted here ([WBLD-06](../../reviews/review-2026-11-12-09-52-30/findings/web-build.md#wbld-06)) | Making the normalized graph label-free changes every stored graph hash, so it needs its own story with a migration of stored versions. Shared fixtures remove today's disagreement without touching a hash |
| **F2. A person's routine keeps the run limit** | [R-52](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-52) | The Routines API keeps the workspace's per-run limit for a routine a person creates. The cronjob tool's US$1 cap stays on routines the model creates. Triggers and timezones become one definition for both, and the budget difference is an explicit parameter ([PDOM-02](../../reviews/review-2026-11-12-09-52-30/findings/py-domain.md#pdom-02)) | The tool's cap guards against a model creating spend no person chose. A person choosing a schedule spends within the same limit as any run they start. Lowering people's routines to US$1 would refuse routines they already have |
| **F3. Members don't write Storage directly** | [R-56](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-56) | A new ordered bootstrap file revokes members' insert, update and delete on Storage objects, unless the implementation finds a browser path that writes them, in which case that path is kept and named. Members keep their write grants on workflow drafts, and the API tolerates a draft that fails validation, behind a forward-migration check ([SQLI-07](../../reviews/review-2026-11-12-09-52-30/findings/sql-infra.md#sqli-07), [SQLI-13](../../reviews/review-2026-11-12-09-52-30/findings/sql-infra.md#sqli-13)) | The service writes artifact bytes through its own role, so a member's write can only turn a published artifact into a missing one (LM-05). The draft grants are accepted by US-15.12 and US-15.2, so removing them would overturn accepted scenarios |
| **F4. The live executor re-qualification waits for the owner** | [R-57](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-57) | The browser images are bound to their source fingerprint, so the current executor qualification reads as stale until it is run again. That live re-qualification is not run here; the refactor's evidence names the command (Decision 0018 B8) | Re-qualifying runs the real images against the install. Until it is done, browsing stays off, which is the safe state, rather than trusting images whose source changed |
| **F5. A system actor for transitions no one leases** | [R-60](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-60) | SP-010's actor table gains `system`, for the transitions that neither a person nor a leased worker makes, such as an expiry or a recovery. Each command lists exactly which actors may apply it, and `system` may apply only the commands its writers already make today | Those writes happen now, outside the command table. Naming their actor puts them through the same checks as every other transition without granting anything new |
| **F6. DH-03 follows the code's layout** | [R-64](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-64) | DH-03 is amended to describe the layout as it is: the worker and process configuration in `operations/`, the database tools under `scripts/`, the database types as a drift-checked exposure artifact, and graph wiring in the goal-loop modules under `application/` ([XMOD-13](../../reviews/review-2026-11-12-09-52-30/findings/sweep-boundaries.md#xmod-13)) | The worker is launched by the Makefile, the install and four scripts, and `app_db` is named in over a hundred files. Moving code to match the document would break entry paths for no behaviour change |
| **F7. Job dispatch belongs to the worker process** | [R-42](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-42) | When `goal_loop` is split, claiming a job, binding it and driving it (`process_next`, `JobBinder`) move to `operations/job_dispatch.py`, which the worker imports. The goal loop itself stays in `application/` and imports nothing from `operations/` | Dispatch is the worker process's step and needs the checkpoint adapter's qualification check. In `application/` it would add an application-to-adapters import, which Decision 0027 D4 counts as legacy and lets only fall; in `operations/` it adds no exception, since no application module imports it |
| **F8. The receipt and approval state tables enter the Option B contract** | [R-50](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-50) | The Option B contract gains a subsection, beside SP-010 and apart from run status, with the receipt and approval state tables exactly as `domain/effects.py` permits them: no new state and no new move. The decision commands use the contracts' existing Literals, and no public schema changes for them | SP-010 asks for these machines to be documented apart from run status. Writing down what the code already enforces adds no behaviour, so nothing accepted is overturned, and a later change to either table now has a named place to be argued |
| **F9. A malformed routine trigger is a malformed request** | [R-52](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-52) | The Routines API types a routine's trigger with the cronjob tool's schedule, so a person's trigger that doesn't fit it is refused like any other strict request field: `422 invalid_request`. The domain keeps `interval_invalid`, `daily_time_invalid` and `trigger_unknown` for the cronjob tool and for stored triggers, and `timezone_unknown` for a zone that doesn't exist, on both paths. An empty timezone, or one over 64 characters, is a malformed field like any other. Stored triggers and their receipts keep their bytes; `record_version` is written only when it isn't 1. A request is fingerprinted from its normalized record, so one sent with an explicit null, such as `"minutes": null`, and retried across the upgrade is an idempotency conflict, not a replay. A stored daily time that isn't text is never scheduled | A typed trigger in the public schema lets the generated client catch a wrong shape before it is sent ([XTYP-08](../../reviews/review-2026-11-12-09-52-30/findings/sweep-types.md#xtyp-08)). The three codes are named by no SPECS scenario, PRD, browser spec or database check, so no accepted behaviour changes, and the request is refused either way |
| **F10. Spend is scoped as admission enforces it, in one SQL fragment** | [R-60](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-60) | The ledger's spend under a root is defined once, as the SQL fragment admission uses today (`root_run_id` is the root), and admission, the run projection and the workflow overview share it. A child run's view adds the calls it made itself, so its spend is its own, never 0 (US-11.12 N-9). Admission is unchanged, and no migration adds a SQL function | A fragment changes no schema, so it needs no guarded apply on an install and can be changed again in one commit. Admission is the check that stops spend, so its definition is the one kept, and the views adapt to it without overturning an accepted scenario ([PRUN-09](../../reviews/review-2026-11-12-09-52-30/findings/py-run.md#prun-09)) |
