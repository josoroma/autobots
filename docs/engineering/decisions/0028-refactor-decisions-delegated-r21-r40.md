# Decision 0028: Choices made while delivering refactor items R-21 to R-40

**Date:** 2026-11-14. **Authority:** the owner, by delegation. They asked to work "from R-21 to R-40" of [the code-quality review's refactor plan](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md) and to "take responsible and senior and hard decisions that require a human interaction for me". [Decision 0027](0027-refactor-decisions-delegated.md) records the same delegation for R-01 to R-20, and its principles carry over.

Each choice below is one the plan left to the owner. Where two options were close, the one that is reversible, fails closed on money and keeps a run resumable was chosen. A later owner decision replaces any of them.

| # | Item | Choice | Why |
|---|---|---|---|
| **E1. A moved base returns to review, and the wait follows the retry** | [R-21](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-21) | When an approved pull request's base has moved, `approvals.return_to_review` holds the lease, settles the receipt, returns the request to pending with `DEFAULT_TTL_SECONDS` and appends `approval.requested`, in one transaction that a stale generation can't enter. The call still ends `base_moved` (Decision 0022 D15), and the run enters the decision wait when the call is tried again, as before. It does not enter the wait at once ([XDUP-02](../../reviews/review-2026-11-12-09-52-30/findings/sweep-duplication.md#xdup-02)). Until the call is retried, a person deciding the renewed request is refused with `approval_run_not_waiting`; if it is never retried, the request expires. An attempt whose lease was lost wrote nothing and doesn't use the person's decision, so the run's next owner can use it | Entering the wait inside the pass was tried and isn't safe yet. A person's pause or cancel during the GitHub reads makes the transition refused, which would roll back the return to pending; and `base_moved` is in none of the loop's stop sets, so the pass would end as a lost lease and a parent would see its assignment lost rather than paused. Doing it needs a "returned to review" stop with its own disposition in the loop middleware, the goal loop and the workflow runner, and a rule for a pause or cancel during the reads. This is final, not deferred: no effect can happen without a fresh decision either way, so consent is never weakened, and the model is told `base_moved` and asks again when it retries. The cost is a short gap in which deciding early is refused with a clear reason, which is smaller than the risk of three run-control modules changing for a rare path |
| **E2. Unreadable spend fails closed** | [R-23](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-23) | The paid-run watchdog stops the worker, as it does on a cap breach, after 3 consecutive polls on which the committed spend can't be read. The run's report records the spend as unknown, the ledger entry is settled as held rather than released, and the entry point exits non-zero. A single unreadable poll is logged and counted. A poll that can't run at all (the database or psql raises) stops the worker at once, recorded as `watch_failed`, since nothing is watching the spend after it. An unknown spend is counted at the run's whole limit in every total | Each unreadable poll used to be skipped, so a database that stopped answering left a paid worker unwatched ([SCRP-03](../../reviews/review-2026-11-12-09-52-30/findings/scripts.md#scrp-03)). Stopping costs one unfinished trial; spending past the shared cap can't be undone |
| **E3. An unmapped stop code pauses** | [R-29](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-29) | Every known stop code has an explicit disposition, tested exhaustively. A code missing from the table suspends the run (paused, resumable) with a warning log, instead of failing it | A failed run can never resume (SP-010), so a new or misspelled code silently ended runs for good ([PRUN-02](../../reviews/review-2026-11-12-09-52-30/findings/py-run.md#prun-02)). A pause is visible to a person and reversible, and the exhaustive test keeps the table complete for every code the code base knows |
| **E4. Worker failures are bounded** | [R-35](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-35) | A pass that raises an unclassified exception is recorded privately (`failed_attempts` and the qualified exception type, never its message) and released with a backoff of 30 s, then 60 s. The third consecutive failure suspends the run with the stop code `worker_failed` through the canonical transition. A pass that completes resets the count, and so does a person's resume. A run a person is cancelling can't be suspended, so at the bound its cancellation is settled as `finish` settles it, on a live lease only. If that settlement itself keeps failing, the run stays cancelling, retried every 60 s and logged at error each time, since SP-010 forbids finishing a cancel without classifying what is in flight | SP-012 requires bounded retries, and no bound existed: a deterministic bug was reclaimed after every lease period with no durable reason ([PRUN-14](../../reviews/review-2026-11-12-09-52-30/findings/py-run.md#prun-14), [XERR-10](../../reviews/review-2026-11-12-09-52-30/findings/sweep-errors.md#xerr-10)). Three attempts ride out a transient fault; a paused run stays resumable and shows why it stopped |
| **E5. One way to show money and time** | [R-37](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-37) | Where the web's copies disagreed, the variant most screens showed was kept, unless it understated a cost or a limit. Money reads "US$" with two decimals and more digits only when the amount has them (up to six), never rounded, so a sub-cent spend no longer reads as US$0.00. Durations and past relative times round half away from zero at the smallest unit shown, in whole words. Time left before a deadline, such as an approval's expiry, rounds down. Status words and tones are keyed by the generated `RunStatus`, so a new status fails the type check. Every changed string is listed in the refactor's evidence | A spend or limit shown smaller than it is invites a wrong decision about money, and time left shown longer than it is invites a missed deadline. Everything else follows what most screens already said, which changes the fewest strings people have seen |
| **E6. A preview shows the model that will run** | [R-31](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-31) | A workflow's preview shows each agent step the model its child run will actually use: the workflow run's resolved policy, which the child inherits. The step Expert's own role bindings are no longer applied in the preview, since the run doesn't apply them. A step's child keeps the workflow run's policy rather than following its Expert's bindings ([PPRD-09](../../reviews/review-2026-11-12-09-52-30/findings/py-product.md#pprd-09)); an Expert's bindings apply when it runs on its own | A preview that names a model the run won't use misleads a person about what they pay for. A run keeps the policy it froze at admission (PRD-Model-Providers MP-01), so a workflow's steps run on the model chosen when the workflow was admitted, and a step that switched to its Expert's model would spend on one nobody chose then |
| **E7. Where shared run types live** | [R-33](../../reviews/review-2026-11-12-09-52-30/refactor-plan.md#r-33) | `ModelRoute` moves from the loop middleware adapter to `domain/models.py`, beside the profiles and role policy, and the adapter imports it back. The rate-limited log helper `Repeated` moves to a small domain module that the operations logs import back, as they already do the secret patterns. `loop_registry` moves to `application/loop_tools.py`, the home R-42 names. So the run lifecycle module holds `LoopConfig` whole and `workflow_runner` never imports `goal_loop` | Each is a pure value or rule that two layers need. Moving it down to the domain adds no layer exception (Decision 0027 D4), where keeping it in an adapter or in operations would have added one or split `LoopConfig` in two |
